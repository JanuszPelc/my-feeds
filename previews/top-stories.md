<h2>Go Security Team Advises on Mitigating CVE-2026-98432 Linux Kernel Flaw</h2>
<a name="story-26027"><img src="https://wsrv.nl/?url=https%3A%2F%2Fnews-pravda.com%2Fimg%2F20261031%2F82035a6900331972800bc4ed99426020.jpg&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>The Go Security Team has issued guidance regarding CVE-2026-98432, a critical use-after-free vulnerability affecting IPv4 TCP connection handling in the Linux kernel that can allow remote code execution when Multipath TCP listeners are exposed. While upgrading to a patched kernel remains the definitive fix, Go 1.24 and later versions enable Multipath TCP by default for listen sockets on Linux, making programs potentially susceptible unless mitigated.</p><p>Developers can disable Multipath TCP globally at runtime using the "GODEBUG=multipathtcp=0" environment variable, at build time by adding "godebug multipathtcp=0" to a go.mod file, or explicitly per socket using Dialer and ListenConfig settings. However, the security team cautions that program-by-program mitigations are fragile and stresses that updating the kernel is the only complete remedy, noting that any future changes to Go's default behavior will be discussed publicly.</p>

<h2>Pivot Database Engine Explains Impact of Memory Latency on Database Performance</h2>

<p>High database CPU utilization frequently masks underlying memory stalls rather than intense computation, as modern RAM access speeds lag hundreds of instructions behind CPU processing capabilities. A naive GROUP BY implementation causes frequent cache misses that force the processor to wait on cold memory from DRAM.</p><p>To mitigate this bottleneck, the Pivot database engine implements a two-phase radix partitioning approach that breaks down large aggregation tasks into smaller pieces. By ensuring that working hash tables fit within the CPU caches, this optimization significantly reduces DRAM load operations and accelerates query execution times.</p>

<h2>Go 1.28 HTTP/2 Parking Mechanism Reduces Server Memory Usage</h2>
<a name="story-26028"><img src="https://wsrv.nl/?url=https%3A%2F%2Fabdolirad.me%2Farticles%2Fgo-1-28-http2-parking-memory%2F01-rss-scaling.svg&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>An analysis of the draft Go 1.28 release notes examines a new HTTP/2 server mechanism called parking, which allows connection-serving goroutines to exit when there is no active work instead of waiting idle. Benchmarks comparing a Go 1.28 development build with parking enabled versus disabled show that handling 5,000 idle HTTP/2 connections results in 5,000 fewer active goroutines and a resident set size (RSS) reduction of roughly 85 to 93 MiB.</p><p>The benchmark results indicate that enabling parking lowers stack memory usage by approximately 78 MiB under the same load, while heap allocation metrics remain variable across test runs. Because the feature is evaluated on a pre-release development build using an experimental and temporary debug setting, the findings highlight potential memory efficiency gains for servers maintaining thousands of idle connections rather than guaranteed outcomes for all workloads.</p>

<h2>Avoid Public Functions Calling Other Public Functions</h2>
<a name="story-26064"><img src="https://wsrv.nl/?url=https%3A%2F%2Fsubstackcdn.com%2Fimage%2Ffetch%2F%24s_%217ki7%21%2Cw_1200%2Ch_675%2Cc_fill%2Cf_jpg%2Cq_auto%3Agood%2Cfl_progressive%3Asteep%2Cg_auto%2Fhttps%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F0c53ebbb-678b-4a7d-8ea3-cae7d5f26e4d_4000x3000.png&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>When developing software modules, developers should avoid having public functions call other public functions to satisfy the DRY principle. This practice creates tension between designing an interface convenient for external callers and one easy to reuse internally, often leading to interface degradation and bloated optional parameters.</p><p>Instead, developers should extract shared implementation logic into a private helper function that both public functions can call. An exception to this rule applies to shortcut APIs, where public functions are intentionally defined as chains of calls to other public functions to serve as genuine shortcuts.</p>

<h2>The Kluever Maneuver for Two-Commit Bug Fixes</h2>
<a name="story-26055"><img src="https://wsrv.nl/?url=https%3A%2F%2Fwww.gitkraken.com%2Fwp-content%2Fuploads%2F2021%2F07%2Fdiff-between-commits.png&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>The Kluever Maneuver is a software development practice that splits a bug fix into two distinct commits: the first introduces a failing test that exposes the bug, while the second applies the fix and updates the test to pass. This structured approach ensures continuous integration passes at every commit and avoids false confidence from tests that might inadvertently pass before a fix is implemented.</p><p>By separating the demonstration of failure from the fix itself, developers gain verifiable proof that their code changes actually resolved the targeted issue. The technique also helps maintain clear version control histories and allows developers to easily link initial test commits directly to bug tracking systems.</p>
