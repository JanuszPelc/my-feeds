<h2>`kill(1)` Parsing Bugs in `procps` Impact Ubuntu LTS Releases</h2>
<p>Multiple Ubuntu LTS releases, from version 14.04 to 24.04, have contained bugs in the `kill(1)` command within the `procps` package. These issues stem from the use of `getopt` for command-line parsing, which causes negative process group identifiers (pgids) to be incorrectly interpreted as unrecognized options. In some cases, this misparsing leads to signals being sent to all processes on a machine except for PID 1.</p><p>Four distinct bugs were identified where previous attempts to fix parsing errors introduced new issues like segmentation faults or unintended shell termination. Because `kill` arguments can function as either signal names, numbers, or PIDs, `getopt`'s handling of option bundling is problematic for this utility. Positional argument parsing, similar to the implementation in FreeBSD, is recommended to ensure more predictable behavior.</p>
<p><small>Links: <a href="https://alangrow.com/blog/a-decade-of-kill-bugs">alangrow.com</a> | <a href="https://lobste.rs/s/wgoato/decade_kill_bugs">lobsters</a></small></p>

<h2>Examination of Early Unix Memory Allocation and Malloc History</h2>
<a name="story-26221"><img src="https://wsrv.nl/?url=https%3A%2F%2Fnapcakes.nekoweb.org%2Fposts%2Fmalloc%2Funix-v4-tape.jpg&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>An analysis of early Unix source code traces the evolution of memory allocation from primitive linear allocators in Unix Version 4 to explicit map-based memory management and eventual modern malloc implementations. Early Unix versions utilized straightforward linear allocation routines using sbrk without freeing memory, while kernel routines managed partitioned resources such as main memory and swap space using explicit resource maps.</p><p>The historical survey highlights how subsequent editions introduced allocation macros, size-computation shortcuts, and zero-initialization practices that predated or influenced modern language features like C++'s new operator. By examining historical source trees via the Unix Tree repository, the post documents the iterative design choices made by early Unix developers under strict hardware constraints.</p>

<h2>The Origins and Early Development of BSD Unix</h2>
<a name="story-26194"><img src="https://wsrv.nl/?url=https%3A%2F%2Fimage4.slideserve.com%2F9082739%2Fthe-bsd-unix-l.jpg&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>In the late 1970s, Bill Joy and researchers at UC Berkeley created the Berkeley Software Distribution (BSD) by bundling a Pascal compiler, line editors, and other utilities as an add-on package for AT&amp;T Unix. By distributing these tools at cost, Berkeley fostered a tradition of sharing that helped spread Unix throughout universities and research institutions.</p><p>Following the release of the expanded 2BSD distribution, the acquisition of a VAX computer at Berkeley led graduate student Ozalp Babaoglu and Bill Joy to add virtual memory support to Unix 32/V. Their work culminated in 3BSD in December 1979, drawing the interest of DARPA and laying the groundwork for Unix's widespread adoption in government-funded research.</p>

<h2>Ouros Haskell Processor Implemented on FPGA</h2>
<a name="story-26179"><img src="https://wsrv.nl/?url=https%3A%2F%2Fbathtub-01.github.io%2Ftechnical%2Fouros-demo%2Fdemo.gif&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>Researcher Yukang Xie has demonstrated Ouros, a dataflow-driven graph reduction processor designed for lazy functional languages like Haskell, running natively on an FPGA board. The hardware architecture executes compiled combinator graphs directly, providing built-in support for automatic fine-grained multi-threading and concurrent garbage collection without a software runtime or kernel trap.</p><p>The system incorporates a simplified AXI4-Lite IO interface and UART polling, allowing standalone Haskell programs to perform register-level input and output operations. Synthesized on an AUP-ZU3 FPGA, the processor operates at 100 MHz while utilizing roughly 27% of logic utilization and 40% of block RAM, proving that direct hardware execution of functional languages is viable within a modest circuit budget.</p>
