<h2>`kill(1)` Parsing Bugs in `procps` Impact Ubuntu LTS Releases</h2>
<p>Multiple Ubuntu LTS releases, from version 14.04 to 24.04, have contained bugs in the `kill(1)` command within the `procps` package. These issues stem from the use of `getopt` for command-line parsing, which causes negative process group identifiers (pgids) to be incorrectly interpreted as unrecognized options. In some cases, this misparsing leads to signals being sent to all processes on a machine except for PID 1.</p><p>Four distinct bugs were identified where previous attempts to fix parsing errors introduced new issues like segmentation faults or unintended shell termination. Because `kill` arguments can function as either signal names, numbers, or PIDs, `getopt`'s handling of option bundling is problematic for this utility. Positional argument parsing, similar to the implementation in FreeBSD, is recommended to ensure more predictable behavior.</p>

<p>Developer Chris Wellons has released Prospero, a lightweight C++ coding harness designed for local LLMs and AI agents. <h2>Abhinav Sarkar Implements LC-3 Disassembler in Haskell</h2>
<a name="story-26088"><img src="https://wsrv.nl/?url=https%3A%2F%2Fmedia.cheggcdn.com%2Fmedia%2F838%2F838e66d6-7ba4-4b13-9279-f2ddad8a8d28%2Fimage.png&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>Abhinav Sarkar details the implementation of a disassembler for Little Computer 3 (LC-3) binaries written in Haskell. Because LC-3 object files intermix raw instructions and data without section or symbol tables, the disassembler employs a multi-pass heuristic approach that performs unambiguous decoding, speculative context-based decoding, data cleanup, and label insertion.</p><p>The walkthrough covers setting up mutable vectors and strict ST monads in Haskell, utilizing type-safe bit matching with GHC pattern synonyms, and parsing binary formats to reconstruct readable textual assembly.</p>

<h2>Avoid Public Functions Calling Other Public Functions</h2>
<a name="story-26064"><img src="https://wsrv.nl/?url=https%3A%2F%2Fsubstackcdn.com%2Fimage%2Ffetch%2F%24s_%217ki7%21%2Cw_1200%2Ch_675%2Cc_fill%2Cf_jpg%2Cq_auto%3Agood%2Cfl_progressive%3Asteep%2Cg_auto%2Fhttps%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F0c53ebbb-678b-4a7d-8ea3-cae7d5f26e4d_4000x3000.png&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>When developing software modules, developers should avoid having public functions call other public functions to satisfy the DRY principle. This practice creates tension between designing an interface convenient for external callers and one easy to reuse internally, often leading to interface degradation and bloated optional parameters.</p><p>Instead, developers should extract shared implementation logic into a private helper function that both public functions can call. An exception to this rule applies to shortcut APIs, where public functions are intentionally defined as chains of calls to other public functions to serve as genuine shortcuts.</p>
