<h2>Rust Lock Poisoning Defended in Blog Post</h2>
<a name="story-28689"><img src="https://wsrv.nl/?url=https%3A%2F%2Fi.ytimg.com%2Fvi%2FCelSS20DRGQ%2Fmaxresdefault.jpg%3Fsqp%3D-oaymwEmCIAKENAF8quKqQMa8AEB-AH-CYAC0AWKAgwIABABGH8gUSgTMA8%3D%26rs%3DAOn4CLAvjpH3HMffriIky2444px8LSoZsw&amp;w=1200&amp;h=1200&amp;fit=inside&amp;we&amp;output=jpg&amp;bg=white" width="30%" align="right" /></a>
<p>In response to a proposal to make Rust's default mutex non-poisoning by silently unlocking on panic, software engineer sunshowers argues that lock poisoning is an essential mechanism for maintaining system correctness. The article details how unexpected panics and cancellations during critical sections can permanently violate mutex invariants and logically corrupt shared data.</p><p>While many applications abort on panic or handle errors via results rather than panics, default unwinding in multithreaded code creates risks where invariant failures go unnoticed unless detected. The author contends that lock poisoning provides a critical advisory heuristic to catch these corrupted states, drawing parallels to similar risks posed by future cancellations in asynchronous Rust.</p>
